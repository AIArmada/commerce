# Organizations Audit

## Packages Reviewed
- `packages/organizations` (`aiarmada/organizations`) — core domain: `src/Models/Organization.php` (sole model; membership rows owned by `aiarmada/membership` via `HasMembers`), `src/Actions` (7: `CreateOrganizationAction`, `TransferOrganizationOwnershipAction`, `ArchiveOrganizationAction`, `RestoreOrganizationAction`, `SuspendOrganizationAction`, `MakeOrganizationPublicAction`, `MakeOrganizationPrivateAction`), `src/Contracts` (6: `OrganizationAuthorization`, `OrganizationProfileExtension`, `OrganizationVisibilityTransitionAuthorizer`, `CurrentOrganizationResolver`, `OrganizationPresentation`, `OrganizationLifecycleHook`), `src/Resolvers` (5: `Default*` ×3, `Null*` ×2), `src/Http/Middleware/CurrentOrganizationMiddleware.php`, `config/organizations.php`, `database/migrations/2000_01_01_000001..000002` (`organizations`, `organization_members`), `src/OrganizationsServiceProvider.php`, `CONTEXT.md`, `docs/01-overview.md`, `03-configuration.md`, `04-usage.md`, `99-troubleshooting.md` (+ `02-installation.md`). No `routes/`, no `tests/`, no factories/seeders.
- `packages/filament-organizations` (`aiarmada/filament-organizations`) — Filament adapter: `src/Resources/OrganizationResource.php` (+ `RelationManagers/MembersRelationManager.php`, `InvitationsRelationManager.php`, `Pages` ×4), `src/FilamentOrganizationsPlugin.php`, `src/FilamentOrganizationsServiceProvider.php`, `config/filament-organizations.php`, `CONTEXT.md`, `docs`. No `routes/`, no `tests/`.

## Overall Assessment
- Quality: Tightest pair in this audit batch. Single-aggregate design (`Organization` + membership invariants), contract-first extensibility (authorization, visibility authorizer, lifecycle hook, presentation, profile extension), correct owner-primitive wiring (binds `OwnerResolverInterface` → `CurrentOrganizationResolver`, middleware establishes `OwnerContext`), immutable `created_by`, transactional ownership transfer, `public()` scope discipline. Filament resource correctly delegates authorization and scopes the list query to the viewer's memberships.
- Health risks (ranked): (1) **Duplicate membership storage** — `organizations` migration creates `organization_members` while `membership.HasMembers::membersTable()` derives `{basename}_members` from `membership.pivot.table_suffix` and `Organization::membersTable()` overrides it from `organizations.database.tables.members`: two configs, one physical table, neither package clearly owns the schema; (2) **Missing uniqueness** — no unique on `organizations.slug`, no unique on `(organization_id, user_id)` in members table, so duplicate slugs and double memberships are insertable and `ownerMember()->exists()` checks become unreliable; (3) **Thin config surface** — only `database.tables` + `resolver` + `middleware.require_context`; no `json_column_type` (no JSON columns — fine), no table-prefix support, `resolver` read at `registeringPackage()` time (config-cache timing hazard); (4) **Overlapping tenant-adjacent concepts** — `organizations.Organization` (tenant aggregate, IS the owner) vs `persons.Affiliation.institution_id` (loose institution pointer that may reference an org) vs `customers` owner tuple vs `membership` invitations/applications: no documented map for which "organization" a `Customer` belongs to vs which `Organization` owns it; (5) zero tests in both packages for the ownership invariant (single owner, no second owner, final owner cannot leave).
- Refactor size: Small-Medium. One migration batch (uniques), one config/provider hardening, Filament hardening (slug handling, delete policy, invitation scoping), contract documentation, Pest suites. Estimated ~10 files touched, no new tables, no data backfill beyond dedup before uniques.

## Migration Impact

## Package Responsibilities
- `organizations` owns: the reusable tenant aggregate (`Organization` model: identity, status/visibility enums, `published_at/privatized_at/suspended_at/archived_at/last_state_change_at` lifecycle), membership ownership invariants (`assertMemberCanBeAdded/CanBeRemoved/RoleCanChange` via `MembershipMutationGuard`), lifecycle actions (create/archive/restore/suspend/public/private/transfer), current-org context (`CurrentOrganizationResolver`, `CurrentOrganizationMiddleware` → `OwnerContext`), and the `OwnerResolverInterface` binding for the whole monorepo.
- `organizations` does NOT own (per CONTEXT guardrails): join/invite flows (belongs to `membership`), events/addresses/media/billing/moderation, public projections/profile extensions (host-provided via `OrganizationProfileExtension`/`OrganizationPresentation`), Filament UI.
- `filament-organizations` should own only: `OrganizationResource` + member/invitation managers + lifecycle-action buttons. It currently does, with correct delegation to `OrganizationAuthorization`.

## Deep-Dive Findings, Second Pass (2026-09-07 re-audit)

### O-A6 — `created_by` immutability is model-guarded but action-uncovered
- Severity: Low
- Location: `packages/organizations/src/Models/Organization.php:184` (`if ($organization->exists && $organization->isDirty('created_by'))` guard in `saving`), `packages/organizations/src/Actions/*.php` (7 actions, none sets `created_by` except `CreateOrganizationAction`)
- Problem: The `created_by` immutability invariant lives ONLY in the model's `saving` hook. Positive: the guard exists (verified line 184). Gap: none of the 7 actions documents whether it preserves or reassigns `created_by` on transfer/restore paths, and `TransferOrganizationOwnershipAction` changes the OWNER role without touching `created_by` (correct — creator ≠ owner — but undocumented, so a future contributor will "fix" it by syncing the two).
- Why It Matters: Creator-vs-owner conflation is the classic tenant-audit bug: compliance reports join `created_by` expecting the founder and get the current owner instead.
- Recommended Fix: Docs-only: one paragraph in `docs/04-usage.md` ("`created_by` is the founding user, immutable forever; ownership lives on the members pivot and moves via transfer; the two are never synced") + a Pest assertion (`transfer preserves created_by`) in the new suite. No code change.
- Breaking Change: NO | Affected Packages: `organizations` | Required Dependent Changes: None. | Migration Required: NO
- Re-check: CONFIRMED 2026-09-07 — `saving` guard present at line 184; `TransferOrganizationOwnershipAction` touches only pivot roles + Spatie sync, never `created_by`.

### O-D3 — `organization_members` uses a surrogate UUID PK while sibling pivots use composites
- Severity: Low
- Location: `packages/organizations/database/migrations/2000_01_01_000002_create_organization_members_table.php` (`$table->uuid('id')->primary()`), vs `customers` pivots (`primary(['segment_id','customer_id'])`)
- Problem: Inconsistent pivot style repo-wide (customers audit already flags the composite side). The surrogate `id` is harmless here (membership rows carry `role` + `joined_at` and are addressed individually by `MembersRelationManager`), but the inconsistency means the `(organization_id, user_id)` uniqueness backstop (O-A1 fix) must be an explicit unique index rather than falling out of a composite PK.
- Why It Matters: Prevents a naive "standardize pivots" refactor from dropping the surrogate and silently changing `MembersRelationManager` route keys.
- Recommended Fix: Keep the surrogate PK. Document the exception in `docs/03-configuration.md` ("members table keeps a surrogate PK because relation managers address rows individually").
- Breaking Change: NO | Affected Packages: `organizations` | Required Dependent Changes: None. | Migration Required: NO
- Re-check: CONFIRMED 2026-09-07 — migration emits surrogate PK + non-unique composite index only.

## Final Recommended Architecture
- `Organization` stays the single tenant aggregate and the monorepo's `OwnerResolver` source: one table, one slug unique, one membership unique, code invariants backed by DB uniques, lifecycle timestamps centralized in a shared transition helper.
- `membership` owns invitation/join mechanics and the pivot write path but MUST honor `MembershipMutationGuard`; `organizations` owns the invariant definitions and the current-org context. The members-table name has exactly one source of truth (`organizations.database.tables.members`).
- Filament remains a thin, membership-scoped adapter with lifecycle actions surfaced (not just list/view) and every member-mutating ID re-authorized. No owner-scope on `Organization` itself (it IS the owner) — scoping lives downstream via the `OwnerContext` this package establishes.
