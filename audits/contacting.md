## Overall Assessment
- Quality: Strongest core in this batch and the reference implementation for owner-scoped polymorphic attach: `HasOwner`+`HasOwnerScopeConfig` on all 3 models, `OwnerWriteGuard`-backed `ContactingModelReferenceGuard` on every write path, `OwnerContext::withOwner` in snapshot persistence, `OwnerUiScope` in all 3 Filament resources, `HasContactMethods/HasSocialProfiles` cascade deletes, per-channel normalize actions, `SocialProfileConfig` prefix/suffix URL builder, `ContactMethodData::email/phone/website` named constructors. Real adoption proves the design (`customers.Customer` + `customers.Address`, `affiliates.Affiliate`, `events.Venue`/`EventOrganizer`, `feedback` models all use the traits).
- Health risks (ranked): (1) **Dual contact storage with no canonical rule** — adopters keep native `email`/`phone`/`website`/`contact_email` COLUMNS alongside contacting rows (`customers.Customer.email/phone`, `customers.Address.phone`, `events.EventOrganizer.email/phone`, `events.Venue` computed accessors, `affiliates.Affiliate.contact_email/website/phone` + pending-write accessors): every read must decide column-vs-row, every write must sync both, and `Customer.getFormattedAddress/toShippingLabel` already encode divergent fallback logic; (2) **Primary-flag races + asymmetric implementations** — `ContactMethod::syncSiblingPrimaryFlags` locks parent + siblings transactionally while `SocialProfile::syncSiblingPrimaryFlags` is a bare mass-update with no lock/transaction and no owner scoping on the demote query; neither has a DB backstop; (3) **`order_column`/`sort_order` alias hack** — both models expose `order_column` get/set aliases over the real `sort_order` column (migration has only `sort_order`), suggesting a half-finished rename that doubles the API and risks Filament table-sorting on a non-column; (4) **Snapshot semantics half-built** — `CreateContactSnapshotAction::persistSnapshot` returns an UNSAVED model when `features.contact_snapshots=false` (silent no-persist), `fromBundle` loops N+M saves with no transaction, snapshots carry `owner` copied from source but `snapshotable` owner unchecked; (5) **Inconsistent timestamps** — contacting migrations use `$table->timestamps()` (tz-naive) while every other pair in this batch uses `timestampsTz()`, and lifecycle columns are correctly `timestampTz` — mixed precision in one table; (6) zero tests despite being the most-depended-upon package in the batch.
- Refactor size: Small-Medium, code-only. Unify primary-flag sync, remove/finish the alias hack, make snapshot persistence explicit, document the column-vs-row canonical rule, align timestamps on next table touch, add Pest suites. Estimated ~12 files touched, 1 new file max (`Support/ContactPrimaryGuard` or shared trait), no structural migration strictly required.

## Package Responsibilities
- `contacting` owns: polymorphic contact methods (`ContactMethod` + `HasContactMethods` + create/update/normalize/set-primary), social profiles (`SocialProfile` + `HasSocialProfiles` + same), contact snapshots (`ContactSnapshot` + `CreateContactSnapshotAction`), channel normalization (email/phone/URL/handle normalizers + `SocialProfileConfig` URL builder), link building (`BuildContactLinksAction`), reference guard (`ContactingModelReferenceGuard`).
- `contacting` does NOT own: message sending history (belongs to `communications`), customer/affiliate/event domain logic (consumers), address geography (belongs to `addressing`).

It currently does — the thinnest adapter in the batch, correctly delegating normalization/validation to core.

## Deep-Dive Findings, Second Pass (2026-09-07 re-audit)

### T-M5 — `normalizeForSave` unconditionally overwrites an explicitly-set `display_value`
- Severity: Medium
- Location: `packages/contacting/src/Models/ContactMethod.php::normalizeForSave()` (`$this->display_value = $normalized['display_value'];` unconditional), `packages/contacting/src/Models/SocialProfile.php::normalizeForSave()` (rewrites `handle`/`url`/`normalized_url` unconditionally)
- Problem: Save-time normalization rewrites user input on EVERY `saving` — including admin typo-corrections that get "fixed" back. Concretely: an operator setting `display_value = "+60 12-345 6789 (ext 5)"` for display fidelity has it overwritten by the normalizer's canonical form on the next update of ANY field on the row. `country_code` uppercasing runs before normalization (order correct — verified), and `guardAllowedType` runs after (wasted work on typo'd types, harmless).
- Why It Matters: Display fidelity loss; operators learn they cannot correct formatting, so they stop correcting data.
- Recommended Fix: Preserve explicit display: only fill `display_value` when it is null/unchanged-dirty (`if (! $this->isDirty('display_value')) $this->display_value = $normalized['display_value'];`). Keep `normalized_value` always overwritten (it is the search/dedup key). Same guard for `SocialProfile::handle`/`url` only when the operator did not explicitly set them.
- Breaking Change: NO (explicit values now stick; null behavior unchanged) | Affected Packages: `contacting` | Required Dependent Changes: None. | Migration Required: NO
- Re-check: CONFIRMED 2026-09-07 — `normalizeForSave` assigns `normalized_value` + `display_value` unconditionally on every `saving`; no `isDirty` check.

### T-C5 — `SocialPlatform::label()` reads config at runtime (enum depends on config)
- Severity: Medium (unchanged — incremental path confirmed)
- Location: `packages/contacting/src/Enums/SocialPlatform.php:56,67` (`config('contacting.social_profiles.platforms.' . $this->value)`), `packages/contacting/config/contacting.php` (`social_profiles.platforms` 45 entries, `strict_social_platforms=false`, `strict_contact_types=false`)
- Problem: A backed enum — a value type that must be stable under config caching and Octane — reads mutable config on every `label()` call. Under `config:cache` with a trimmed platforms map, `label()` returns null for valid cases; under Octane, a config reload mid-request changes display strings. `strict_*` flags default false, so typo'd platforms persist silently alongside.
- Why It Matters: Enum identity and display metadata are conflated; display overrides cannot be distinguished from identity validation.
- Recommended Fix: Incremental (no big rename): make the enum cases the identity source of truth (the 45 platforms as cases, no config reads for identity); keep config ONLY for display `label/prefix/suffix` overrides with a null-safe fallback to the case name. Filament selects source from `SocialPlatform::cases()`. Keep `strict_*=false` defaults (no behavior change now).
- Breaking Change: NO | Affected Packages: `contacting`, `filament-contacting` | Required Dependent Changes: Filament form schemas source options from the enum. | Migration Required: NO
- Re-check: CONFIRMED 2026-09-07 — `SocialPlatform.php:56` reads per-platform config, `:67` reads the full map; both `strict_*` flags default false.

### T-F5 — Importer resolves no owner per-row (bulk forgery surface, verify-and-harden)
- Severity: Medium (flagged as verify-and-harden, not failed)
- Location: `packages/filament-contacting/src/Imports/ContactMethodImporter.php` (zero `Owner|owner|withOwner` references — verified via rg), `packages/filament-contacting/src/Imports/SocialProfileImporter.php`, exporters (scoping unconfirmed)
- Problem: The importers ship disabled-by-default (`features.imports=false`) but the code path exists: each CSV row creates a contact row without per-row owner resolution. Today's safe state rests entirely on the feature flag + relation-manager-first defaults (`standalone_resources=false`). The moment a host flips `imports=true`, bulk cross-owner creation opens.
- Why It Matters: Bulk import is the highest-volume forgery surface in the package; row-by-row `contactable_type/id` from CSV is attacker-controlled.
- Recommended Fix: Per-row `OwnerWriteGuard::findOrFailForOwner` in both importers + `OwnerUiScope` in both exporters; Pest test with a cross-owner CSV row (rejected, siblings untouched). Gate the `imports=true` rollout on these tests.
- Breaking Change: NO | Affected Packages: `filament-contacting`, `contacting` | Required Dependent Changes: None. | Migration Required: NO
- Re-check: CONFIRMED-AS-FLAGGED 2026-09-07 — `rg Owner|owner|withOwner …/ContactMethodImporter.php` returns zero hits; exporter scoping likewise unconfirmed.
