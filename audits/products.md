## Packages Reviewed (bullets)
- `packages/products` (`aiarmada/products`) — core domain: `src/Models` (10: `Product`, `Variant`, `Option`, `OptionValue`, `Category`, `Collection`, `Attribute`, `AttributeGroup`, `AttributeSet`, `AttributeValue`), `src/Actions` (5), `src/Contracts` (4), `src/Enums` (6), `src/Events` (5), `src/Policies` (6 + `Concerns/HandlesOwnerScoping.php`), `src/Concerns` (2), `src/Traits/HasAttributes.php`, `src/Strategies/MatrixVariantGenerator.php`, `config/products.php`, `database/migrations/2001_01_01_000001..000014`, `database/factories/*`, `resources/lang/*`, `src/ProductsServiceProvider.php`, `docs/01..05 + 99`
- `packages/filament-products` (`aiarmada/filament-products`) — Filament adapter: `src/Resources` (`ProductResource`, `CategoryResource`, `CollectionResource`, `AttributeResource`, `AttributeGroupResource`, `AttributeSetResource`, `BaseProductResource`, `BaseCatalogResource`, `BaseAttributeResource` + Pages/Schemas/Tables/RelationManagers), `src/Support/ProductStatsAggregator.php`, `src/Widgets/*` (4), `config/filament-products.php`, `src/FilamentProductsServiceProvider.php`, `src/FilamentProductsPlugin.php`, `docs/01..04 + 99`

## Overall Assessment (quality, health, risks, refactor size)
- Quality: Catalog modeling is thoughtful (minor-units pricing, `HasOwner` on all 10 models, enum-cast statuses, variant matrix generator behind interface, policies for six models, abstract `Base*Resource` DRY layers in filament). The EAV attribute subsystem (4 entities + 3 pivots) is the most complex in the four pairs and carries the most risk.
- Health risks: (1) `FilamentProductsServiceProvider` never calls `hasConfigFile()` — `config/filament-products.php` is dead; all `config('filament-products.*')` reads fall back to literals, so publishing/editing config is a no-op; (2) `products.features.owner.enabled=false` hardcoded (not env) while policies default to `enabled=true` — models unscoped, policies assume scoped (or vice versa); (3) `owner_scope` string + `(owner_type, owner_id)` tuple dual ownership on 7 tables with uniques keyed on the string, not the tuple — cross-tenant uniqueness broken; (4) `store_money_in_cents` toggle allows major-units storage, violating the minor-units invariant every consumer assumes; (5) three visibility enums + two identical `Is*Entity` traits + three overlapping price contracts; (6) 4 of 10 models lack policies; (7) zero tests.
- Refactor size: Medium-Large. No table rebuild. Fix provider config registration, align owner defaults, remove money toggle, consolidate enums/traits/contracts, add missing policies, scope filament option queries uniformly. Estimated ~20 files touched, ~4 files deleted, no data migration.

## Migration Impact
**Migration Required: NO**
- Tables: `products`, `product_variants`, `product_options`, `product_option_values`, `product_variant_options`, `product_categories`, `category_product`, `product_collections`, `collection_product`, `product_attributes`, `product_attribute_groups`, `product_attribute_values`, `product_attribute_sets`, `product_attribute_attribute_group`, `product_attribute_attribute_set`, `product_attribute_group_attribute_set` (all `config('products.database.tables.*')`). No rename/add/drop recommended.
- Columns: no changes. `owner_scope` columns stay (fix is to stop using them for uniqueness decisions, not to drop them). `store_money_in_cents` behavior is fixed by locking writers to minor units, not by altering column types.
- Indexes/constraints: no `constrained()`/`cascadeOnDelete()` found — compliant. Uniques on `(owner_scope, slug/sku/code)` are wrong-key but changing them to tuple-keyed partial uniques requires dedup cleanup and is explicitly deferred — no migration now. Pivot PK inconsistency (composite vs surrogate `uuid id`) is documented as a style exception, not a migration.
- Data migration: none. If `store_money_in_cents=false` was ever enabled in an environment, that environment needs a one-off major→minor backfill (`price*100`) before locking the flag — call out in release notes, do not automate here.

## Package Responsibilities
- `products` owns: catalog source of truth (products, variants, options, categories, collections, EAV attributes), variant generation (`Actions/GenerateVariants.php`, `Strategies/MatrixVariantGenerator.php`, `Contracts/VariantGeneratorInterface.php`), product lifecycle (`Actions/CreateProduct.php`, `UpdateProduct.php`, `UpdateProductStatus.php`, `ApplyAttributeChanges.php`), pricing/buyable/inventory contracts (`Contracts/Buyable.php`, `Priceable.php`, `Inventoryable.php`), custom-attribute storage (`Traits/HasAttributes.php`, `Models/AttributeValue.php`).
- `filament-products` should own only: six resources + base resources, schemas/tables/infolists, relation managers, stats aggregator + widgets, plugin registration. It correctly owns no tables. Violations: `Support/ProductStatsAggregator.php` + widgets reimplement owner-aware counting that belongs behind a core `ProductStats` query (acceptable as read-only, but must use `OwnerCache`); `ProductForm.php` imports `Customers\Models\Customer` (unused/domain leak — remove).

## Laravel-Specific Findings
- PHP 8.4: compliant (`^8.4`, strict types, enums, promotion, readonly where apt).
- FK constraints: compliant — `foreignUuid`/`nullableUuidMorphs`/`uuidMorphs` throughout with zero `constrained()`/`cascadeOnDelete()`; verified empty grep. App-level deletes: `HasAttributes::bootHasAttributes` deletes `attributeValues` on parent delete (correct); `Product`/`Category`/`Collection` deletes rely on detaching pivots — verify `Product::deleting` detaches `categories/collections` + deletes `variants/options/attributeValues` (if missing, add; cascade must be explicit per repo rules).
- UUID PKs: compliant for entities (`uuid PK` + `HasUuids` + `getTable()` from `products.database.tables.*` with `table_prefix` fallback). Style exception (Low, document don't migrate): pure pivots `category_product`/`collection_product`/`variant_options` use composite PKs while attribute pivots use surrogate `uuid id` + unique pairs — standardize on one pivot style for new tables; leave existing as-is.
- Owner scoping: structure correct (`HasOwner` + `HasOwnerScopeConfig` + `HasOwnerScopeKey` on entities; `ownerScopeConfigKey='products.features.owner'`). Violations: hardcoded-disabled config + policy/model default split (Critical above); manual reimplementation in `Collection::applyOwnerScopeToProductsQuery` (above); filament option queries mix three patterns (`forOwner()`, `OwnerQuery::applyToEloquentBuilder`, `OwnerScopedIds::ensureAllowed/allowedIds`) — all valid, but standardize per surface (tables: `forOwner`; option selects: `OwnerScopedIds`; programmatic: `OwnerQuery`).
- Config discipline: `json_column_type` defined and consumed via `commerce_json_column_type` — compliant. Dead/misleading keys: `database.table_prefix='product_'` is read only as a fallback in `resolveProductTable`/`getTable` while every migration uses explicit `tables.*` names — either wire the prefix (migration rewrite — not recommended) or delete the key (recommended). `media.collections/conversions`, `seo.slug_max_length`, `features.variants.sku_pattern` are read (verified in forms) — keep. Missing: `features.variants.max_generated` (add per above).
- Media/tags plugins: `filament-products/composer.json` correctly requires `filament/spatie-laravel-media-library-plugin` + `spatie-laravel-tags-plugin` (both `^5.7`) matching Filament v5 — no action.

## Final Recommended Architecture
- `products` is the standalone catalog owner: 10 scoped models with tuple-enforced slug/sku identity, minor-units-only pricing via a single `Priceable` contract, capped/queued variant generation, EAV attributes with centralized casting, no `contacting`/`pricing`/`inventory` imports (integration via `class_exists` + contracts only).
- `filament-products` is a thin adapter with live config: six resources over three abstract bases, shared media-form helpers, `OwnerCache`-backed stats, all option IDs via `OwnerScopedIds`, no domain math, no CRM imports.
- Consumers (`checkout`, `inventory`, `pricing`, `events`, `ticketing`, `affiliates`, `promotions`) depend only on `Products\Models\Product/Variant` + `Contracts\Priceable/Buyable/Inventoryable/VariantGeneratorInterface`, always inside an explicit owner context. No consumer imports `FilamentProducts\*`.
