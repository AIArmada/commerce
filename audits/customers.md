## Overall Assessment (quality, health, risks, refactor size)
- Quality: Good coverage breadth (profiles, addresses, segments, groups, notes, resolver, segmentation engine, five policies, three Filament pages). Owner primitives are used correctly (`HasOwner` + `HasOwnerScopeConfig` on all five models, `OwnerWriteGuard`/`OwnerUiScope` in Filament, `forOwner` in commands). The package is let down by duplication and boundary leaks rather than missing features.
- Health risks: (1) owner mode defaults OFF (`customers.features.owner.enabled=false`) for tenant-owned CRM data — insecure default; (2) `Customer.email` indexed but not unique per owner — duplicate/guest-email collisions + cross-tenant resolver reuse; (3) `Segment.slug` unique per `owner_scope` string, not per `owner_type/owner_id` tuple — cross-tenant slug Betrayal; (4) `CreateCustomer` vs `UpdateCustomerProfile` duplicate name/email/phone parsing; (5) merge logic split between core `CustomerResolver::mergeCustomers` and filament `MergeCustomersAction` (domain in adapter); (6) hard `aiarmada/contacting` dependency + `HasContactMethods`/`HasSocialProfiles` traits baked into `Customer`/`Address` — CRM cannot stand alone; (7) zero tests.
- Refactor size: Medium-Large. No table rebuild. Extract shared name/contact parsing, enforce per-owner email uniqueness (code + partial unique index), fix segment-slug scoping, move merge into a core `MergeCustomers` action, soften `contacting` to conditional integration, flip owner default to secure. Estimated ~15 files touched, 1–2 new files, no data migration (unique indexes added online later if desired).

## Migration Impact
**Migration Required: NO**
- Tables: `customers`, `customer_addresses`, `customer_segments`, `customer_segment_customer`, `customer_groups`, `customer_group_members`, `customer_notes` (all `config('customers.database.tables.*')`). No rename/add/drop recommended.
- Columns: no changes. `owner_scope` on `customer_segments` stays as-is (fix is to stop trusting it for uniqueness, not to drop it).
- Indexes/constraints: no `constrained()`/`cascadeOnDelete()` found — compliant. Recommended future hardenings (NOT required now, all online index-only if adopted): partial unique `customers(owner_type, owner_id, email) WHERE email IS NOT NULL`, partial unique `customer_segments(owner_type, owner_id, slug)`, replacing the current `customers_segments_owner_slug_unique(owner_scope, slug)` which keys on the denormalized scope string. No backfill; duplicates must be cleaned before any such index is added — explicitly out of scope for this audit.
- Data migration: none. Resolver/merge fixes are code-only.

## Laravel-Specific Findings
- PHP 8.4: compliant (`^8.4`, strict types, enums, promotion).
- FK constraints: compliant — `foreignUuid`/`nullableUuidMorphs` without `constrained()`/`cascadeOnDelete()`. App-level cascades in `Customer::deleting` (addresses, notes, detach segments/groups), `CustomerGroup::deleting`, `Segment::deleting` (detach) — correct pattern. Harden by wrapping multi-delete in `DB::transaction` (currently sequential; `UpdateCustomerProfile` already uses transactions — extend to `deleting` hooks or move to `DeleteCustomer` action).
- UUID PKs: compliant for entity tables (`uuid PK` + `HasUuids` + `getTable()` from config). Deviation (Low): pivot tables `customer_segment_customer` and `customer_group_members` use composite PKs (`primary(['segment_id','customer_id'])`, `primary(['group_id','customer_id'])`) with no surrogate `uuid id` — inconsistent with `products` attribute pivots (which do use `uuid id`). Acceptable for pure pivots, but standardize on one pivot style repo-wide and document the exception.
- Owner scoping: pattern correct (`HasOwner` + `HasOwnerScopeConfig`, key `customers.features.owner` on all five models). Violations: (1) default OFF (`enabled=false`, `include_global=false`) for tenant-owned CRM — insecure default; flip to `enabled=true` (env-overridable) and verify `checkout`/`cashier` run inside owner context; (2) `Customer::booted` + two concerns triple-implement auto-assign (above); (3) `DB::table` paths: none in `src/` except via `OwnerQuery`-aware command (`RebuildSegmentsCommand` correctly uses `forOwner`/`withoutOwnerScope` with explicit tuple select) — compliant.
- Config discipline: `customers.php` has `database.table_prefix='customer_'` but no table actually uses the prefix (all names explicit in `tables.*`) — dead key; `json_column_type` correctly consumed via `commerce_json_column_type`. `features.segments.auto_assign=true` hardcoded (not env) — make env-driven. `integrations.user_model=null` fallback to `auth.providers.users.model` is correct. Filament config nests `navigation.group` + `resources/pages.navigation_sort` correctly.
- Policies: exemplary coverage — all five models have policies registered in `CustomersServiceProvider::packageBooted`. Verify `CustomerNotePolicy`/`CustomerPolicy` global-record branches (`owner_type===null && owner_id===null` returns) match `include_global=false` default (global rows should be admin-only, not publicly readable).

## Final Recommended Architecture
- `customers` is the standalone CRM owner: five scoped models, `CreateCustomer`/`UpdateCustomerProfile` sharing one normalizer, `CustomerLookup` + `CustomerMerger` behind a thin `CustomerResolver` facade, canonical `MergeCustomers` + `SetDefaultAddress` + `RebuildAllSegments` actions, per-owner email/slug enforcement, optional `contacting` integration behind `class_exists`, no payment code.
- `filament-customers` is a thin adapter: two resources, three pages (forms only), two widgets, all queries via `OwnerUiScope`, all writes via `OwnerWriteGuard`/core actions. No domain actions in adapter.
- Consumers (`checkout`, `cashier`, `ticketing`, `events`, `pricing`) depend only on `Customers\Models\Customer/Segment` + `CustomerResolver`/`MergeCustomers` contracts, always inside an explicit owner context. No consumer imports `FilamentCustomers\*`.
