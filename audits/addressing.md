## Overall Assessment
- Quality: Most feature-complete pair in the batch (polymorphic attach + snapshots + formatting/normalization + geography providers + area/postcode import pipeline + seeders + Malaysia dataset). Conventions largely followed: PHP 8.4 strict types, `HasUuids` everywhere, `getTable()` from config (with one key-path inconsistency, below), `uuid PK`s, no DB FK constraints/cascades, `CarbonImmutable`, app-level cascades (`Address::deleting` clears pivots/assignments, nulls snapshots).
- Health risks (ranked): (1) **Triple address lineage with no migration path** — `addressing.Address` (polymorphic, 40+ columns, geography-linked) vs `customers.Address` (`customer_id` FK, `type` enum, `is_default_*`, own contacting trait) vs `orders.OrderAddress` (order-scoped snapshot-ish) vs `events.Models.Concerns.Addressable` (fourth trait): three tables + two traits for "an address", zero code reuse (`rg Addressing packages/customers/src` hits only provider wiring for validation page; `Customer` never uses `HasAddresses`); (2) **Config key split** — core models read `config('addressing.tables.*')` while `config/addressing.php` defines the section as `tables` nested at top level AND some models read `addressing.tables.*` vs providers reading `addressing.geography.providers`/`addressing.formatters`/`addressing.area_sources`/`addressing.models.*`/`addressing.defaults.*`: works, but `ModelResolver` only covers state/city (not country/area/address), and `Address::addressables()` hardcodes `Model::class` in `morphedByMany` (broken generic); (3) **Redundant denormalized columns** — `addresses` carries BOTH `state_id→states` + free `state` string, `city_id→cities` + free `city`, `country_id→countries` + `country` + `country_code`, plus alias fillables (`lat/lng/google_place_id`) absent from migration; `setAttribute` trims some string columns but not others; (4) **Import/seed surface without tests** — 7 commands + 14 actions + CSV/JSON datasets, zero Pest coverage; (5) Filament exposes 7 resources with `addresses`/`snapshots` resources disabled by default while code ships anyway.
- Refactor size: Large. Requires a canonical-address decision (adopt vs deprecate vs bridge `customers`/`orders` addresses), `ModelResolver` completion, alias/fillable cleanup, Filament dead-resource pruning, and the first Pest suites for attach/primary/snapshot/format paths. Estimated ~25 files touched, 2–3 new files.

## Migration Impact
**Migration Required: NO** — migration track completed 2026-09-07, see `migration-record.md#addressing`

## Package Responsibilities
- `addressing` owns: polymorphic address attachment (`Address`, `Addressable`, `HasAddresses`), address snapshots (`AddressSnapshot`, `CreateAddressSnapshotAction`), formatting/normalization (`FormatAddressAction`, `NormalizeAddressDataAction`, contracts + country resolvers), geographic reference data (countries/states/cities/areas/postcodes + links/roles/relationships/names), import pipeline (`ImportAddressAreasAction`, `ImportPostalCodesAction`, sources), seeding (`Seed*` actions + commands + Malaysia datasets), navigation links (`BuildAddressNavigationLinksAction`).
- `addressing` does NOT own (per CONTEXT): tenant scoping (explicit v1 non-goal — this audit recommends reversing that for instance tables only), org identity, order/customer address lifecycles (today duplicated in `customers`/`orders` — canonicalization decision required).
- `filament-addressing` should own only: 7 resources + schemas/tables/relation managers, import/export surfaces, navigation group/icons/sort from config. Violations: `Support/SingleAddressAreaSource` + `ResolvesAddressingResources` duplicate core resolver logic in the adapter (verify and merge into core `Support/`); `AddressAreaResource::getEloquentQuery()` no-op override adds noise.

## Deep-Dive Findings, Second Pass (2026-09-07 re-audit)

### G-A6 — `DB::table` seed paths touch only global reference data (explicitly exempt)
- Severity: Low (confirmation, not a defect)
- Location: `packages/addressing/src/Actions/SeedAddressCountryReferencesAction.php:77,105,142,156` (`DB::table(config("addressing.tables.{$configKey}"))`, `insertOrIgnore`), `packages/addressing/src/Actions/SearchAddressAreasAction.php:51-52,66-67` (relationship-table joins)
- Problem: None — but the exemption must be pinned: the multitenancy rule requires `OwnerQuery::applyToQueryBuilder` on every `DB::table` path touching tenant-owned data. Addressing's `DB::table` call sites touch ONLY reference tables (countries, currency/timezone links) and the relationship join table — all documented global. A future contributor adding an instance-table `DB::table` fast path will copy this pattern without the owner application.
- Why It Matters: Prevents a "follow the existing pattern" leak when someone optimizes snapshot reads with a raw query.
- Recommended Fix: Docs-only: one comment above each `DB::table` call site ("reference data — intentionally global, no owner scope") + a line in `docs/04-usage.md` ("raw queries against `addresses`/`addressables`/`address_snapshots` MUST apply `OwnerQuery`; reference tables MUST NOT").
- Breaking Change: NO | Affected Packages: `addressing` | Required Dependent Changes: None. | Migration Required: NO
- Re-check: CONFIRMED 2026-09-07 — `rg DB::table packages/addressing/src` hits only `SeedAddressCountryReferencesAction` (reference tables); no `DB::table` against instance tables.

### G-D3 — Snapshot table uses tz-naive `timestamps()` while siblings use `timestampsTz()`
- Severity: Low (explicitly no-migration)

## Final Recommended Architecture
- Two-tier addressing: GLOBAL reference tier (countries/states/cities/areas/postcodes/links — never owner-scoped, curated by seeders/imports, read-only in admin) + OWNER-SCOPED instance tier (`addresses`, `addressables` pivots, `address_snapshots` — `HasOwner`, owner inherited from the attached model, `include_global=false`; pre-migration ownerless rows need a backfill-or-explicit-global decision before prod).
- `addressing.Address` is the canonical forward address for all new polymorphic attachments; `customers.Address` and `orders.OrderAddress` are frozen legacy bridged via `toAddressingData()` + order-time snapshots, not extended.
- All FK/free-text duals resolve FK-authoritative with normalization in one action; config lives at `addressing.database.tables.*` (renamed in one release, no shim); geography extensibility stays contract-first (`CountryGeographyProvider`, `CountryAddressFormatter`, `AddressAreaSource`) with boot-time validation; Filament stays thin (scoped instance resources, unscoped reference resources, no domain sources in the adapter).
