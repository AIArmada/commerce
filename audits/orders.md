# Orders Audit
## Packages Reviewed (bullets)
- `packages/orders` (`aiarmada/orders`) — core domain: `src/Models` (6), `src/Actions` (14 + 2 concerns), `src/States` (13) + `src/Transitions` (12), `src/Services/OrderService.php`, `src/Contracts/*`, `src/Events/*` (17), `src/Listeners/*`, `src/Policies/*` (2), `src/Health/OrderProcessingCheck.php`, `config/orders.php`, `database/migrations/2000_11_01_000001..000006 + 2026_07_13_000001`, `resources/lang/*`, `resources/views/*`, `src/OrdersServiceProvider.php`, `docs/01..06 + 99`
- `packages/filament-orders` (`aiarmada/filament-orders`) — Filament adapter: `src/Resources/OrderResource.php` (+ Pages/Form/Infolist/Tables/RelationManagers), `src/Pages/OrderFulfillmentPage.php`, `src/Pages/OrderTimelinePage.php`, `src/Widgets/*` (4), `src/Support/FilamentOrdersCache.php`, `config/filament-orders.php`, `src/FilamentOrdersServiceProvider.php` (incl. invoice-download route), `src/FilamentOrdersPlugin.php`, `docs/01..05 + 99`

## Overall Assessment (quality, health, risks, refactor size)
- Quality: Strong state-machine modeling (`OrderStatus` + 12 transitions), integer minor-units throughout, `HasOwner` on all 6 models, idempotent intake (`intake_source`/`intake_id` + `OrderIntakeConflictException`), transactional `CreateOrder`, and owner-aware invoice route put this above average. Filament adapter is mostly thin and correctly uses `forOwner` + `Gate`.
- Health risks: (1) `CreateOrder::findExistingIntake` is unscoped — cross-tenant dedup leak; (2) `CreateOrderFromCart` duck-types the cart (`object $cart` + `$cart->subtotal/discount/shipping/tax/total`) with no validation and mismatched field names vs cart core (`discount` vs `discount_total`); (3) `orders.owner.enabled` defaults `false` in core but filament route defaults it to `true` — one of them is wrong in prod; (4) intake unique `[owner_type, owner_id, intake_source, intake_id]` is NULL-unsafe (global duplicates pass); (5) only 2 of 6 models have policies; (6) J&T-specific shipping UI hardcoded in generic orders adapter; (7) zero tests.
- Refactor size: Medium. No table rebuild. Fix intake lookup scoping + NULL-safe dedup (code + partial index), type the cart bridge, register missing policies, move shipping UI behind `FulfillmentHandler`, fix config default alignment, add tests. Estimated ~12–15 files touched, no data migration (unless NULL-safe unique index is added — online `CREATE UNIQUE INDEX ... WHERE` only).

## Migration Impact
**Migration Required: NO**
- Tables: `orders`, `order_items`, `order_addresses`, `order_payments`, `order_refunds`, `order_notes` (all `config('orders.database.tables.*')`). No rename/add/drop recommended.
- Columns: `intake_source`/`intake_id` already added by `2026_07_13_000001`. No new columns required for the fixes in this audit (scoping is a query fix; cart-bridge typing is a code fix).
- Indexes/constraints: no `constrained()`/`cascadeOnDelete()` found — compliant. The NULL-unsafe uniques (`orders_intake_unique` on `[owner_type, owner_id, intake_source, intake_id]`; `order_payments_order_gateway_transaction_unique` on `[order_id, gateway, transaction_id]` with nullable `transaction_id`) should be hardened in a future migration with partial indexes (`WHERE intake_source IS NOT NULL AND intake_id IS NOT NULL`, `WHERE transaction_id IS NOT NULL`), but this audit does not require running it now — application-level `findExistingIntake` + `isDuplicateKeyError` fallback already covers the common path. If added later it is an online index-only migration with no data backfill.
- Data migration: none. Do not backfill `owner_*` or recompute totals; fix writers going forward.

- `orders` owns: order graph (`Order`, `OrderItem`, `OrderAddress`, `OrderPayment`, `OrderRefund`, `OrderNote`), 13-state machine (`States/OrderStatus.php` + per-state classes) + transitions (`Transitions/*`), creation (`Actions/CreateOrder.php`, `Actions/CreateOrderFromCart.php`), payments/refunds (`Actions/RegisterOrderPayment.php`, `Actions/RegisterOrderRefund.php`, `Actions/RefundAllocationValidator.php`), holds/fraud/returns (`Actions/HoldOrder.php`, `ReleaseOrderHold.php`, `FlagOrderAsFraud.php`, `CancelOrder.php`, `CompleteOrder.php`, `ReturnOrder.php`), invoices/receipts (`Actions/GenerateInvoice.php`, `GenerateReceipt.php`, `CreateOrderInvoiceDoc.php`, `CreateOrderReceiptDoc.php`, `DetermineOrderDocumentType.php`), handler extension (`Support/OrderHandlerRegistrar.php`, `Contracts/FulfillmentHandler.php|InventoryHandler.php|PaymentHandler.php`), events, policies, health check.

## Filament Adapter Findings (thin-adapter check, domain leak, duplication, dependency direction)
- Thin-adapter: mostly PASS. No filament-owned tables, no duplicated order math. Exceptions: (1) shipping carrier knowledge in `ViewOrder.php` (move behind `FulfillmentHandler`); (2) `FilamentOrdersCache` reimplements owner-keyed cache keys with raw `Cache::forget` instead of `OwnerCache` primitive — use `OwnerCache::forgetForOwner()` or equivalent so tenant/global invalidation stays consistent; the class itself documents the global+includeGlobal invalidation hole ("cannot invalidate every tenant's cache key") — bound the TTL short (currently unbounded `Cache::forget` model with presumably short-TTL writes elsewhere; verify TTLs are ≤5 min) or switch to per-render computation.
- Dependency direction: correct (`filament-orders` requires `orders`; `orders` never imports `FilamentOrders\*`). `composer.json` suggest of `aiarmada/jnt` is appropriate.
- Navigation: PASS. `navigation.group/sort` nested; `OrderResource::getNavigationGroup()` reads `config('filament-orders.navigation.group','Sales')`, `getNavigationSort()` reads `navigation.sort`; pages do the same; no `static $navigationGroup`.
- Owner + authz: `OrderResource::getEloquentQuery` + `FilamentOrdersServiceProvider` invoice route (`forOwner` + `Gate::allows('view')` + explicit-global 404 guard) are exemplary. Gap: only `Order`/`OrderItem` policies registered (`OrdersServiceProvider::registerPolicies`); `OrderAddress`, `OrderPayment`, `OrderRefund`, `OrderNote` have no policies, yet relation managers (`Items/Payments/Refunds/NotesRelationManager`) expose them. Register policies for all six or gate via parent `Order` policy explicitly in each relation manager + add `OwnerWriteGuard` on write actions.

## Final Recommended Architecture
- `orders` remains the exclusive lifecycle owner: typed creation bridge (`CreateOrder` + typed `CreateOrderFromCart`), fully owner-guarded service (injected actions, `AssertsOrderOwnerBoundary` everywhere), single doc pipeline (`DetermineOrderDocumentType` → `CreateOrder*Doc` → `Generate*`), scoped idempotent intake, six-model policy coverage, transactional deletes with final-state guard.
- `filament-orders` stays a thin adapter: `OrderResource` + fulfillment/timeline pages + widgets reading through `forOwner`, writes through owner-guarded service/actions, carriers resolved via `FulfillmentHandler`, stats behind `OwnerCache`-backed `FilamentOrdersCache`, invoice route throttled + policy-gated.
- Downstream (`checkout`, `inventory`, `events`, `promotions`, `affiliates`, `filament-shipping`, `docs`) depend only on `Orders\Contracts\*`, `Orders\Models\Order`, and stable event shapes. No downstream imports `FilamentOrders\*`.
