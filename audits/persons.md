# Persons Audit

## Implementation outcome (migration track, 2026-09-07)

The owner-column and title-uniqueness migration claims were dropped. Persons is explicitly shared identity data with no current `HasOwner` consumer, and the existing title unique supports the transactional reorder algorithm.

No `routes/`, no `tests/`.

## Overall Assessment
- Quality: Narrow, well-factored identity domain (canonical person + names + titles + credentials + affiliations). Conventions mostly followed: PHP 8.4 strict types, `HasUuids`, `getTable()` from config, `timestampTz` lifecycle columns, no DB FK constraints/cascades, app-level cascades in `booted()`, immutable date casts. Filament adapter is thin and correctly shaped (resources delegate to domain, no domain logic in adapter).
- Health risks (ranked): (1) **Cross-tenant leak by design** — `Person` and all 9 satellite tables are explicitly unscoped ("Shared identity by design") while the polymorphic assignment traits (`HasTitles`, `HasAffiliations`, `HasCredentials`) are documented for attachment to *any* model including owner-scoped ones (`Customer`, `Affiliate`, `Venue`, `EventOrganizer`); an `Affiliation`/`TitleAssignment` attached to tenant A's customer is readable by tenant B — no `owner_type/owner_id` on any persons table to even express ownership; (2) **Wrong unique on `titles`** (`category_id, usage_position, sort_order` unique) makes `sort_order` a key rather than an ordering hint and fights `ReorderTitleAction`; (3) **Dead identity plumbing** — `slug`/`searchable_name` columns exist on `persons` but nothing ever writes them (no boot hook, no action, no Sluggable concern), `PersonData` carries `slug`/`status` that have no write path; (4) **`institution_id` loose UUID** with no validation, no relation, nullable-everywhere (`affiliations.institution_id`, `title_issuers.institution_id`, `credential_assignments.issuing_institution_id`, `titles.country_id`, `persons.nationality_country_id`) — dangling references are undetectable; (5) **Identity duplication across packages** — `persons.Person` (shared, unscoped, title/credential/affiliation-centric) vs `customers.Customer` (owner-scoped, `first_name`/`last_name`/`email`/`phone` + own `customer_addresses` table + contacting traits) vs `organizations.Organization` (tenant aggregate) vs `events.EventOrganizer`/`Venue` (own `email`/`phone` columns + contacting traits): four overlapping notions of "who is this" with no documented ownership map, no `person_id` link from `Customer`, and `customers` explicitly told "Skip when: Person identity — see persons" while duplicating every person field; (6) zero tests in both packages.
- Refactor size: Medium-Large. Code-only fixes (drop wrong unique, wire slug/searchable generation, validate institution/country refs, harden Filament ID validation) plus a **data migration** (owner morphs on the three polymorphic assignment tables + `affiliations`, or an explicit documented decision that persons data is global with per-attach authorization). Estimated ~14 files touched, 1–2 new files (`AssignTitleAction`/`GeneratePersonIdentityAction` or owner concern), 1 migration batch.

## Migration Impact
**Migration Required: YES**
- Tables: `persons`, `person_names`, `title_categories`, `titles`, `title_issuers`, `title_assignments`, `credential_definitions`, `credential_assignments`, `affiliations`, `affiliation_roles` (all `config('persons.database.tables.*')`). No renames, no drops.
- Columns to ADD (nullable, backfill-free): `owner_type` (string, nullable) + `owner_id` (uuid, nullable) via `nullableUuidMorphs('owner')` on `title_assignments`, `credential_assignments`, `affiliations` (the three tables whose `*_able_type/id` can point at owner-scoped models). `person_names`, `affiliation_roles` inherit owner via parent — no columns. `persons` itself stays global (shared identity) — explicit decision, documented.
- Indexes/constraints to CHANGE: (a) DROP the wrong unique `titles_category_usage_sort_order_unique (category_id, usage_position, sort_order)` — `sort_order` is an ordering hint, not an identity key; replace with plain index on `(category_id, usage_position, sort_order)`; (b) ADD `unique(['person_id','name_type','language_code','full_name'])` or at minimum `index(['person_id','is_primary'])` to make primary-name lookup cheap (currently only `index(['person_id','name_type'])`); (c) ADD `unique('slug') WHERE slug IS NOT NULL` once slug generation is wired (see findings) — add after backfill, not before; (d) ADD composite `index([titleable_type, titleable_id, status])`, `index([credentialable_type, credentialable_id, status])`, `index([affiliatable_type, affiliatable_id, is_primary])` for the hot read paths (`Person::getFormattedNameAttribute`, relation managers).
- Data migration: none required for existing rows (new owner columns nullable; unscoped reads keep working until enforcement is flipped on). Backfill slugs/searchable names via one artisan/command run after code lands (idempotent `whereNull('searchable_name')` update), then add the partial unique.
- Constraints/cascades: none currently (`foreignUuid` never used in persons migrations; all FK columns are plain `uuid()->index()`), so nothing to drop — remain constraint-free per repo rule; new owner columns must also be constraint-free (`nullableUuidMorphs`, no `constrained()`).

## Package Responsibilities
- `persons` owns: canonical person identity (`Person`, `PersonName`), title taxonomy (`TitleCategory`, `Title`, `TitleIssuer`, `TitleAssignment`), credential taxonomy (`CredentialDefinition`, `CredentialAssignment`), institutional linkage (`Affiliation`, `AffiliationRole`), polymorphic attach traits (`HasTitles`, `HasAffiliations`, `HasCredentials`), title ordering (`ReorderTitleAction`), host-model resolution (`Support/ModelResolver`, `helpers.php`).
- `persons` does NOT own (per its `CONTEXT.md` guardrails): event involvement/roles, members/users, donations, institutions/organizations themselves (only loose `institution_id` pointers), addresses/contact points (belongs to `addressing`/`contacting`), customer CRM (belongs to `customers`).
- `filament-persons` should own only: `PersonResource`/`TitleResource`/`TitleIssuerResource`/`CredentialDefinitionResource` + schemas/tables/relation managers/pages, navigation group/sort from config. It currently does — no domain logic detected in the adapter (only thin `ReorderTitleAction` calls from `TitleResource` pages, which is the correct direction).

## Deep-Dive Findings, Second Pass (2026-09-07 re-audit)

### P-A6 — `Title::country()` falls back to the abstract `Model::class` (broken generic)
- Severity: Medium
- Location: `packages/persons/src/Models/Title.php::country()` (`$countryClass = ModelResolver::countryClass() ?? Model::class`), `packages/persons/src/Support/ModelResolver.php::countryClass()`
- Problem: When `persons.models.country` is unset or points at a missing class, the relation binds `belongsTo(Model::class)` — the abstract base Eloquent model, which has no table and can never resolve. Same defect class as `addressing.Address::addressables()` binding `morphedByMany(Model::class)`. The failure surfaces as a confusing "table not found" on eager-load, not as a configuration error.
- Why It Matters: Hosts running without `addressing` get a broken relation instead of a clear diagnostic; `Title` eager-loads (`Person::getFormattedNameAttribute` → `title.category`, plus any `with('title.country')`) fatal instead of degrading gracefully.
- Recommended Fix: Return a null-safe path: when `countryClass()` is null, `country()` should return a `belongsTo` against the configured class only when set, otherwise expose `country_id` as a raw attribute with a documented "unresolved" accessor (`getCountryNameAttribute()` returning null). At minimum, throw `LogicException('Set persons.models.country …')` at relation-build time instead of binding the abstract model.
- Breaking Change: NO (currently fatal; explicit exception is strictly better)
- Affected Packages: `persons`, `filament-persons`
- Required Dependent Changes: None.
- Migration Required: NO
- Re-check: CONFIRMED 2026-09-07 — `Title.php` lines 62–71 bind `Model::class` fallback; `ModelResolver::countryClass()` returns null when `persons.models.country` is unset or `class_exists` fails.

### P-C5 — `helpers.php` morph-map registration is host-called, never core-called
- Severity: Low
- Location: `packages/persons/src/helpers.php` (`persons_table()`, `persons_register_morph_map()`), `packages/persons/src/PersonsServiceProvider.php` (does not call either)
- Problem: The package ships morph-alias helpers but never invokes them; `CONTEXT.md` says "the app registers its morph map" while no test, seeder, or provider path demonstrates the call. Assignment traits are documented "morph-alias-agnostic" but nothing pins `titleable_type` values to short aliases vs FQCNs, so one host writes `person` while another writes `App\Models\Person` for the same row shape.

- Recommended Fix: Docs-only: add a canonical `docs/04-usage.md` snippet calling `persons_register_morph_map('person')` from the host `AppServiceProvider`, and make `TitleSeeder`/factories use the alias. No code change.
- Breaking Change: NO | Affected Packages: `persons` | Required Dependent Changes: None. | Migration Required: NO
- Re-check: CONFIRMED 2026-09-07 — `rg persons_register_morph_map packages/persons/src` hits only the helper definition; provider never calls it.

### P-M5 — `PersonName` rows are reachable without touching `Person`
- Severity: Medium
- Location: `packages/persons/src/Models/PersonName.php` (direct `person_id` FK, no owner columns), `packages/persons/database/migrations/2000_01_01_000011_create_person_names_table.php`
- Problem: `PersonName` inherits ownership conceptually via `person_id`, but `PersonName::query()` is directly queryable (Filament `NamesRelationManager` lists them) with no scope. Once `Person` rows become tenant-linked (via the `person_id` bridge on `Customer`), name rows for tenant A's people remain globally listable. The audit's owner-morph plan covers the three polymorphic assignment tables but not `person_names` — this finding records the deliberate exclusion and its boundary: names are safe ONLY while `Person` itself stays global.
- Why It Matters: If a future change scopes `Person` per-tenant, `person_names` silently becomes the leak. The decision must be pinned in code+docs now.
- Recommended Fix: Document on `PersonName` (docblock + `docs/01-overview.md`): "names inherit the globality of `persons`; do NOT scope `Person` without scoping this table in the same release." Add covering index `index(['person_id','is_primary'])` (see Migration Impact) so the primary-name hot path stays cheap regardless.
- Breaking Change: NO | Affected Packages: `persons` | Required Dependent Changes: None. | Migration Required: YES (index only, fold into batch)
- Re-check: CONFIRMED 2026-09-07 — `person_names` migration carries only `index(['person_id','name_type'])`; no `is_primary` covering index.

### P-D3 — `person_names` lacks a primary-per-scope backstop
- Severity: Medium
- Location: `packages/persons/database/migrations/2000_01_01_000011_create_person_names_table.php`, `packages/persons/src/Models/PersonName.php::booted()`
- Problem: Same race class as the organizations single-owner finding: `is_primary` demotion is a read-then-write `saved`-hook with no DB backstop, and (unlike `Affiliation`) it does not even lock the parent with `firstOrFail` — it is `lockForUpdate()->firstOrFail()` on `$name->person()`, which is present, but concurrent inserts both see no primary and both commit. No partial unique exists.
- Why It Matters: Two primary names per `(person_id, name_type, language_code)` scope; `getFormattedNameAttribute` does not read names today but Filament primary badges become ambiguous.
- Recommended Fix: Fold partial unique `unique(['person_id','name_type','language_code']) WHERE is_primary` into the migration batch (after dedup); keep the hook as the fast path with `wasChanged('is_primary')` guard.
- Breaking Change: NO | Affected Packages: `persons` | Required Dependent Changes: None. | Migration Required: YES
- Re-check: CONFIRMED 2026-09-07 — migration has no partial unique; hook has no `wasChanged` guard (runs on every `saved` with `is_primary=true`, including no-op saves).

### P-F5 — `PersonsTable` searches `name`, not the `searchable_name` index
- Severity: Low
- Location: `packages/filament-persons/src/Resources/PersonResource/Tables/PersonsTable.php`, `packages/persons/database/migrations/2000_01_01_000010_create_persons_table.php` (`searchable_name` indexed)
- Problem: The migration pays for a `searchable_name` index that is both never written (P-A3) AND never read by the admin table (which searches the live `name`/`family_name` columns). Two dead surfaces for one intended feature.
- Why It Matters: Wasted write overhead today; after the slug/searchable generation fix lands, the table must be repointed or the index stays dead.
- Recommended Fix: In the same release as the generation fix, point `PersonsTable` search at `searchable_name` with fallback to `name`; keep both columns read-compatible for one release. No migration.
- Breaking Change: NO | Affected Packages: `filament-persons` | Required Dependent Changes: None. | Migration Required: NO
- Re-check: CONFIRMED 2026-09-07 — `rg searchable_name packages/filament-persons/src` returns zero hits.

## Final Recommended Architecture
- `Person` remains the shared global human-identity root (no owner scope on `persons`, `person_names`, taxonomy definitions). The three polymorphic assignment tables (`title_assignments`, `credential_assignments`, `affiliations`) become owner-scoped bridge rows inheriting owner from their `*_able` parent, so the same `Person` can be titled/affiliated differently per tenant without leaking across tenants.
- All country/institution pointers resolve through `ModelResolver` with fail-closed validation when the target package is installed and must stay null when it is not; no DB-level FK constraints ever.
- `Customer`/`EventOrganizer`/`Affiliate` link to `Person` via nullable `person_id` (loose, indexed, constraint-free) instead of duplicating name/email/phone semantics; `Organization` stays a tenant aggregate and is a valid `institution` target only when explicitly configured.
- Filament stays a thin adapter: navigation from nested config, eager-loaded scoped queries, server-side ID revalidation, zero domain logic beyond calling core actions.
